# Part5: v2 Control Panel UI修正

基点: `0315845e3af01eff6b97c6164db3ddc3109b55af`。

対象は、配信一覧の取得判定、管理画面のレイアウト、定期取得中の操作状態と表示位置、v2配信設定への導線です。

## 変更内容

| 問題 | 修正 |
| --- | --- |
| 配信枠が0件の成功応答を未取得として扱う | `/streams`、`/archive/streams`、`/archive/processing-streams`は、取得結果がnilでもJSONの`[]`を返す。ストレージ障害、割当取得障害、権限不足の500/403は維持する。 |
| 長い日本語タブの背景と文字が重なる | 共通Tabsの固定高さを外し、内容に応じた高さと折返しを使用する。縦方向、line variant、Radixのtab/panel参照を維持する。 |
| Node表内でURLが1文字ずつ縦に並ぶ | 狭いセルの内部で画面全体のブレークポイントを使っていた固定幅ラベル列を除く。Nodeの2表は実際の表示領域幅に合わせて既存のカード表示へ切り替える。 |
| 監査ログ・OAuth接続一覧で日付や状態が読めない | 列の最小幅、日付と時刻のまとまり、対象IDとコピー操作、長いUser-Agentの折返しを調整する。 |
| 定期取得でページが先頭へ戻る | DataTableのデータ変更による自動ページリセットを止める。ユーザーによる検索・並べ替えと、件数減少時の範囲補正は維持する。 |
| 定期取得で編集・確認画面が閉じる | Resource、Dashboard、Workers、登録Nodeのcellを固定したReactコンポーネントにする。最新の値・権限・callbackをContextから受け取り、内部のフォーム状態を保持する。 |
| 通常の更新中だけ表が上下に動く | 更新中だけ挿入していた段落を、固定サイズの更新アイコンとアクセシブルな状態通知に置き換える。初回読込・エラー・権限不足・未取得・古いデータの説明は残す。 |
| 監視・ダッシュボードも更新中に上下に動く | 通常の定期取得中は取得済みsnapshotの説明を保つ。更新中の通知は読み上げ用に残し、部分取得・取得失敗・状態不明を正常扱いにしない。操作許可に使うfresh判定は変更しない。 |
| v2の蓋画像プリセットを管理できない | ウォーターマークの管理ページに蓋画像プリセットの作成・編集・削除と画像アップロードを追加する。Discord配信先プリセットにも不足していた操作を接続する。 |
| 作成権限だけではv2設定を選べない | 新規配信枠のビジュアル設定には`streams.create`、既存枠には`streams.update`を使う。 |
| 更新通知が待機中も空のstatusとして残る | 読み上げ領域を維持し、更新中だけ内容のあるstatusを公開する。Nodeの英語通知も`Refreshing`に揃える。 |
| 390px幅の200%拡大でv2設定がはみ出す | fieldsetと設定グループの最小幅を抑え、管理リンクと再取得ボタンは高さと文字の折返しで内容を収める。 |
| 英語の編集見出しと送信ラベルが不自然 | 編集見出しを`Edit`と対象名で表示し、未送信・競合後の送信ボタンは`Update`を使う。 |

## 設定画面

| 設定 | 場所 |
| --- | --- |
| 蓋画像プリセット | 「ウォーターマーク・蓋画像」→「蓋画像プリセット」(`/admin/overlay/#video-cover-presets`) |
| Discord配信先プリセット | 「Discord」→「Discord配信先プリセット」(`/admin/discord/#target-presets`) |
| 配信枠ごとの既定背景・背景画像・表示名・Discord配信先・蓋画像 | `/admin/streams/#create-stream`の「ビジュアル設定」、または停止中の配信枠の編集画面 |
| 配信中の蓋画像の表示・解除 | 既存の配信枠詳細画面 |
| 画面テーマ | 既存のアカウント画面の外観設定 |

配信枠の編集画面からプリセット管理を開くリンクは別タブを使用し、入力中の内容を保持する。プリセットの参照権限だけを持つユーザーも対象ページへ到達し、閲覧可能なタブが最初に選択される。

画像は既存の認証付きmedia APIで登録・検証する。新しいAPI、データベース移行、配信中の背景変更は追加しない。画像のアップロードには既存APIが要求する`streams.create`または`streams.update`が必要であり、フォームにその条件を表示する。プリセット編集権限で保存済み画像の名前・有効状態を変更する操作は可能。

## 保存と再取得の動作

- プリセット取得失敗、0件、権限不足を区別して表示する。取得失敗で既存の選択を空にしない。
- 配信枠の保存済みプリセットは、自動で最新版に置き換えない。更新ありの表示と明示的な適用操作を提供する。
- 蓋画像の「開始時に表示」だけを変える場合は`cover_start_active`だけを送信し、既存の画像を保持する。
- 編集開始時のrevisionを保持する。一覧の再取得やQueryClientの更新によって、古い入力内容に新revisionを付け直さない。
- Discord・蓋画像プリセットの削除には、確認した対象の`expected_revision`をJSON bodyで送る。確認後に対象が変わった場合は再確認を求める。
- 失敗した再読込では入力内容と画像参照を保持する。保存結果が不明な操作を自動で再送しない。

## 検証

関連するチェック（ローカルでは作業環境のリソース制限に従い、対象を絞って順番に実行する。production buildや全GoテストはCIで確認する）:

```bash
cd web
npm ci
npm run typecheck
npm run lint
npm run test:release-ui
npm run test:ui-regression:components
npm run test:stream-regressions
npm run test:control-platform
```

Goの空一覧テストは`internal/httpapi/stream_list_response_contract_test.go`にある。実ルーターと認証を通して3つの一覧の成功・500・403を検証し、元のnil応答では成功ケースだけが失敗する。

通常のnon-rootブラウザ環境:

```bash
cd web
AUTOSTREAM_BROWSER_PATH=/usr/bin/google-chrome npm run test:release-ui-browser
```

このチェックでは、OAuthの未保存入力とフォーカス、登録Nodeの未送信確認画面、Workersの2ページ目と表の表示位置を実際の定期GETの前・途中・後で確認する。別のレイアウトチェックで長い日本語タブ、NodeのURL、監査ログとOAuth一覧を表示し、指定時にスクリーンショットを保存する。使用するデータはテスト用fixtureである。

監視・ダッシュボードは1440/390pxで定期GET前・取得中・取得後の文言、表示位置、scrollYを比較する。v2設定は作成権限だけで操作可能なこと、参照専用ユーザーの閲覧、503/403と200の空一覧、保存済み画像の編集、409競合で入力を保持し自動再送しないことを実Chromeで検証する。409はテスト用のPUTにだけ返し、実APIへの書込みは行わない。

監視・ダッシュボードの文言比較は既存の固定表示時計を使用し、日付の分境界による揺れを防ぐ。定期GET、応答待ち、native timerと`performance.now()`は実時間で確認する。既存の観測器・fixture・条件台帳を使い、強制配色の5画面と390px・CSS拡大200%の配信設定4条件を追加確認する。元の4144条件のCI matrixも維持する。

CIの`Release UI polling, layout and presets`を独立した必須ジョブとして追加する。既存のチェックは維持する。スクリーンショットの保存先は`AUTOSTREAM_UI174_EVIDENCE_DIR`で指定できる。

## 適用範囲と残る確認

本変更はControl Panelのソース変更であり、本番での配信開始、録画、Remux、Driveアップロードを実施した証拠にはならない。ローカルでのビルド成功と、本番反映・実画面確認を区別する。

既存APIの不足として、次の2点は別途契約の確認が必要になる。

- 背景の任意の単色指定: 現行`background_mode`は`default`または`image`で、色を保存するフィールドはない。既定背景と画像は操作できるが、任意色を保存できたようには表示しない。
- 蓋画像プリセットを配信枠へ適用する直前のrevision競合: 読取には`cover_preset_revision`があるが、更新入力には期待するプリセットrevisionがない。管理プリセット自体の編集・削除は`expected_revision`で保護する一方、配信枠への適用時に別ユーザーがプリセットを更新した場合はサーバーの最新版をsnapshotする。選択時の版を必ず適用するには保存APIの契約追加が必要になる。Discord配信先は既存`preset_revision`を送る。

本番の更新には、この変更を含む正確なcommitのCIと通常のControl Panelリリース手順を使用する。Encoder/Updaterの移行スクリプトを再適用する必要はない。OAuth接続に実際の再認証要求がある場合は、その接続について通常の再認証を行う。表示上の修正によって認証エラーを正常扱いにはしない。
